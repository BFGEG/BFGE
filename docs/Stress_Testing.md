# Нагрузочное тестирование BFGE

## Масштабирование нагрузки

Профиль [stress-scaling.json](stress-scaling.json) последовательно показывает
250, 500, 1000, 1500, 2000, 3000, 4000, 6000, 8000 и 12 000 кубов. Каждый куб находится
на отдельном узле, все используют один меш. Объёмная сетка плавно вращается;
заголовок окна и терминал показывают текущее количество объектов. Для каждого
уровня задано 3 секунды прогрева и 8 секунд измерения при 1280×720 и VSync.

```bash
bash scripts/run-stress-scaling.sh
```

Для построения сводки нужен Python 3. Скрипт повторяет весь набор три раза
в отдельных процессах. В каталоге
`target/stress-scaling/<дата>-<номер процесса>/` появляются три исходных JSON
и `summary.md` с таблицей FPS, худшей полной секунды и p95 времени прохода.
Сводка отмечает наибольший **проверенный** уровень, где средний FPS каждого
прогона и FPS каждой полной секунды не ниже 60. Чтобы выбрать другой ориентир,
запустите, например:

```bash
BFGE_TARGET_FPS=90 bash scripts/run-stress-scaling.sh
```

При ошибке Wayland на работающем X11 используйте
`env -u WAYLAND_DISPLAY bash scripts/run-stress-scaling.sh`. FPS ограничен VSync;
худшая секунда и p95 помогают заметить просадки при хорошем среднем значении.
Если граница попала между двумя уровнями, можно уточнить её дополнительными
числами объектов в `stress-scaling.json` и повторить прогон.

## Основной прогон

Профиль [stress-baseline.json](stress-baseline.json) проверяет 1000 отдельных кубов
на 1000 узлах с одним общим мешем: 12 000 треугольников, 1280×720, FIFO/VSync,
10 секунд прогрева и 60 секунд измерения. Кубы размещены в объёмной сетке;
камера и свет фиксированы, а сетка плавно вращается.
Параметры следуют [протоколу референса](https://github.com/alken1t15/simple-3d-engine/blob/main/docs/requirements.md),
где описаны около 1000 объектов, 10 секунд прогрева, не менее 60 секунд замера,
FPS, время кадра, просадки и память. В референсе это пока план измерения,
а не опубликованный результат нагрузки.

Из корня репозитория на машине с графической сессией запустите:

```bash
bash scripts/run-stress-baseline.sh
```

Если X11 доступен, а переменная Wayland указывает на недоступный сеанс:

```bash
env -u WAYLAND_DISPLAY bash scripts/run-stress-baseline.sh
```

Скрипт один раз собирает release-бинарник и выполняет три независимых запуска
процесса. Каждый запуск ограничен 120 секундами. Отчёты `run-1.json` —
`run-3.json` и сведения о версии кода, состоянии рабочей папки, Rust и ОС
попадают в новый каталог `target/stress-baseline/`. В JSON указаны GPU,
графический backend и сведения о драйвере. Сравнивайте FPS всех трёх прогонов,
медиану/p95/p99 полного прохода, секундные значения `frame_windows` и ряд RSS.
`frame_windows` позволяет увидеть длительные просадки, которые скрывает общая
медиана. При VSync FPS ограничен частотой вывода; результаты относятся к
указанному оборудованию и настройкам, а не задают универсальный порог.

## Диагностические сценарии

Конфигурация [stress-config.json](stress-config.json) фиксирует разрешение 800×600,
FIFO/VSync, прогрев 2 секунды перед каждым измерением, 3 секунды на обычный
сценарий и 60 секунд на длительный сценарий. Числа выбраны как исходный ряд
для сравнения отдельных факторов, а не как основной 60-секундный замер.

Запуск в release-сборке из корня репозитория:

```bash
cargo run --release --locked --features stress-benchmark --bin bfge-stress -- scene-only docs/stress-config.json target/stress-scene-only.json
cargo run --release --locked --features stress-benchmark --bin bfge-stress -- window docs/stress-config.json target/stress-window.json
```

Выходные JSON остаются в игнорируемом Git каталоге `target/`; сводные
исходные измерения для ревью размещаются в описании PR.

Для прогона на X11 (если сеанс также предоставляет Wayland) можно запустить
собранный бинарник командой:

```bash
timeout 180s env -u WAYLAND_DISPLAY target/release/bfge-stress window docs/stress-config.json target/stress-window.json
```

`scene-only` измеряет только `SceneManager::build_render_frame` и RSS процесса;
в этом режиме FPS и полный проход отсутствуют. `window` требует доступного
оконного дисплея и GPU, проверяет фактический размер окна и поддерживаемость
FIFO, затем измеряет подготовку, полный проход и FPS. Полный проход включает
неблокирующий опрос событий, анимацию сетки кубов, сборку кадра, вызов
`render` и `present`.
Завершения работы GPU он не ожидает. FPS вычисляется как число завершённых
проходов, делённое на фактическую длительность измерения. Перцентили времени
считаются по всем кадрам методом ближайшего ранга; JSON содержит гистограммы
в наносекундах для повторного анализа. Оконный режим также сохраняет FPS и
p95 полного прохода по интервалам примерно в одну секунду. Память — `VmRSS`
и `VmHWM` из `/proc/self/status` раз в секунду; это RAM процесса, без видеопамяти.

В диагностических сценариях генерируются одни и те же процедурные треугольники по
указанным параметрам. `meshes: 1` означает общую геометрию для всех объектов;
`meshes: 500` — 500 отдельных ресурсов с отличающимися углами и цветом.
`nodes` включает корень, `depth` — число рёбер от корня. Сначала строится цепочка
нужной глубины, остальные узлы распределяются по допустимым родителям.
Объекты прикрепляются к узлам по кругу. Это синтетическая нагрузка на сборку
сцены и рендер, без загрузки файлов моделей и анимации. Измерение начинается
после построения сцены и прогрева, поэтому не включает стоимость создания
геометрии, узлов и GPU-буферов.

Для проверки зависаний оконный прогон стоит запускать с внешним ограничением
времени, превышающим сумму прогрева и измерений, например через `timeout` на
Linux. Сбой или превышение лимита означает незавершённый прогон; новый отчёт
тогда не записывается. Разрешение, режим синхронизации, CPU и адаптер GPU записываются
в отчёт. Изменения RSS во время длительного прогона следует оценивать по
секундным отсчётам; удержание памяти аллокатором и гистограмма измерений
также влияют на RSS.

Результаты являются исходными измерениями. Пороговые значения не заданы, и
прохождение требований по производительности по ним не объявляется.
